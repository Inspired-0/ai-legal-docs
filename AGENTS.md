# Работа в AI Legal Docs

Целевая концепция с 30.10.2026: самостоятельные правовой MCP, юридический плагин и IDE.
Границы и порядок разработки: [концепция](docs/specs/modular-legal-platform.md),
[дорожная карта](docs/plans/active/modular-platform-roadmap.md). Они описывают будущие
модули; ограничения реализованного демо ниже сохраняются.

Python 3.11+ демо: извлечение полей → детерминированные расчёты → заполнение синтетического DOCX.
Это не сервис реальных договоров. Общие инструкции для Codex, Claude Code и разработчиков.
Отдельный рабочий IDE-прототип: `ide_agent.py`, `ide_server.py`, `prototypes/legal-ide/`;
запуск и ограничения — [live-ide](docs/runbooks/live-ide.md). Он работает с внешним API
и предложениями правок синтетического текста; инвариант шаблонного текста ниже относится
к исходному DOCX-конвейеру, не запрещает явно выбранный пользователем агентный эксперимент.

## Начало сессии

1. Прочитай [карту документации](docs/INDEX.md) и [текущее состояние](docs/CURRENT_STATE.md).
2. Проверь `git status --short`; сохрани чужие изменения.
3. Открывай только нужные spec/plan и код. Перед сквозной правкой прочитай
   [архитектуру](docs/architecture.md). Документы и Git — память, чат — рабочий контекст.
4. Явные требования задачи имеют приоритет над проектными соглашениями. Сверяй документацию
   с тестами, интерфейсами и кодом; существенные конфликты фиксируй в плане, не разрешай догадкой.

## Карта репозитория

- `src/ai_legal_docs/`: `extraction/` — адаптеры; `templates/` — схема, расчёты, рендер;
  `validation/` — проверки; `storage/` — пути вывода; `orchestrator.py` — конвейер.
- `templates/synthetic-service-agreement/` — YAML полей и версионируемый DOCX.
- `examples/` — только синтетические запрос и значения.
- `scripts/` — запуск демо и генератор шаблона.
- `tests/` — pytest и golden структуры DOCX; `.github/workflows/ci.yml` — CI.
- `docs/` — контекст, требования, планы, решения и процедуры.
- `scripts/run_ide.py` — локальный сервер AI-прототипа; ключ только в окружении,
  исходящий контекст после предпросмотра, никакой передачи реальных договоров в тестах.

## Команды из корня

```bash
uv sync --locked --dev
uv run python scripts/run_demo.py
uv run pytest
uv run ruff check .
```

Точечные тесты: `uv run pytest tests/test_extraction.py` (или нужный файл).
Форматирование изменённых Python-файлов: `uv run ruff format <paths>`.
Сборка при изменении упаковки: `uv build`.
Typecheck не настроен. CI запускает Ruff lint и pytest; format/build не входят в CI.
Установка, диагностика и выбор проверок: [runbook](docs/runbooks/development.md).

## Инварианты

- LLM извлекает известные пользовательские поля; правовой текст остаётся в шаблоне.
  Суммы и сумма прописью рассчитываются кодом, не моделью.
- Сохраняй `SYNTHETIC DEMO`, дисклеймеры и вымышленные данные. Не добавляй реальные договоры,
  реквизиты, секреты или логи запросов. См. [SECURITY.md](SECURITY.md).
- Сохраняй публичные интерфейсы и статусы `done`, `needs_input`, `failed`.
  Не выдавай исключение за обработанный статус; `failed` сейчас относится к проверке DOCX.
- Не ослабляй тесты и golden ради зелёного результата. Шаблон меняй по
  [инструкции](docs/template-authoring.md); генератор пока не обеспечивает очистку metadata.
- Меняй только необходимое; новые зависимости должны иметь конкретную причину.
  При изменении зависимостей обновляй `pyproject.toml` и `uv.lock` согласованно.

## Документы и ответы

- При подготовке и редактировании документов, а также при ответах пользователю всегда
  применяй навык `humanizer` (`humanizer:humanizer` в каталоге навыков). Перед первым
  применением в сессии прочитай его `SKILL.md`.
- Пиши естественно и по существу, убирай шаблонные обороты и повторы. Сохраняй смысл,
  факты, точные цитаты и юридические термины; код и неизменяемый текст DOCX-шаблона
  не подвергай стилистической правке.

## Процесс

- Small: изучить → изменить → проверить. Отдельный план не нужен.
- Medium: изучить код/тесты → короткий план в `docs/plans/active/` → небольшие этапы → проверки.
- Large или неоднозначная задача: spec (что) → исследование → план (как) → этапы с проверками
  → независимое ревью в свежем контексте, если доступно. Значимые решения фиксируй в ADR.
- [Шаблоны и правила](docs/runbooks/agent-workflow.md) задают формат spec, plan и handoff.
  После двух неудачных попыток с одной причиной пересмотри предположения и план.
- Для объёмных исследований допустимы read-only subagents, когда делегирование разрешено.
  Параллельные пишущие агенты используют отдельные worktrees/ветки; чужую работу не перезаписывать.
- Выполняй обратимые действия в рамках задачи самостоятельно. Уточнение нужно при существенном
  конфликте требований или неавторизованном разрушительном действии, публикации, изменении
  production либо несовместимом контракте. Не запрашивай повторно уже данное разрешение.

## Готовность и передача работы

- Критерии задачи выполнены, diff просмотрен, нет случайных изменений.
- Для кода выполнены подходящие тесты и Ruff; для шаблона также golden/metadata и визуальное ревью.
  Проверки выбирай по runbook. Сообщай только фактически выполненные команды и результаты.
- Обнови затронутые устойчивые сведения; новый документ добавь в `docs/INDEX.md`.
- Перед завершением длинной работы, compaction или передачей обнови `docs/CURRENT_STATE.md`
  и активный план: результат, проверки, проблемы, следующий конкретный шаг.
  Завершённый план перенеси в `docs/plans/completed/` и исправь ссылки.
- В ответе кратко перечисли изменения, проверки и оставшиеся ограничения.
