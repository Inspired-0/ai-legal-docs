# Архитектура

## Отдельный IDE-прототип

`scripts/run_ide.py` обслуживает интерфейс на loopback через `ide_server.py`.
`ide_agent.py` формирует Chat Completions запрос, заменяет явно перечисленные значения,
проверяет структуру ответа и точное совпадение исходного пункта, восстанавливает значения.
`/api/preview` создает одноразовый ticket на снимок payload; `/api/run` отправляет именно
этот снимок, без автоматических повторов. Максимум 20 ожидающих ticket, срок использования
10 минут, один внешний вызов одновременно. Все состояние в памяти, содержимое не логируется.
Host/Origin и случайный токен ограничивают обращения из других сайтов; статические файлы
отдаются только по allowlist. Ключ хранится в окружении процесса, не выдается браузеру.

`live.js` включает реальный режим только при открытии через сервер; `file://` остается
автономным макетом. Пакет предложений привязан к контексту; принятие обновляет ожидаемый
контекст только собственной операцией. Ручные изменения блокируют старые предложения,
undo не перезаписывает последующий ручной текст. Проверяющий — отдельный вызов без истории
основного чата, но той же модели, без независимого получения законов; `legal_verified=false`.
Клиентский реестр диалогов в app.js хранит документ, страницу PDF, явно добавленный
фрагмент ТЗ, черновик и снимок состояния чата. live.js сохраняет отдельно для каждого
диалога сообщения, предложения, второй анализ, undo и ошибку. Документ редактируется
совместно всеми его диалогами; fingerprint защищает старые предложения. При переключении
отзывается pending preview; до завершения запроса смена диалога/документа блокируется.
Хранение только в памяти страницы, без localStorage и записи на сервер.

Правовая база, NER и native DOCX/PDF не реализованы. [Запуск и проверки](runbooks/live-ide.md).

Ниже описан исходный DOCX-конвейер; его поведение и интерфейсы сохранены.

## Основной поток

`run_pipeline` связывает пять простых шагов.

1. `Extractor` получает текст и список полей.
2. `resolve_values` нормализует значения и проверяет обязательные поля.
3. Та же функция считает суммы строк, итог и сумму прописью.
4. `docxtpl` подставляет данные в готовый DOCX.
5. `RenderedDocumentValidator` ищет открытые слоты, маркер демо и таблицу услуг.

Если обязательных значений нет, конвейер возвращает статус `needs_input` и не создаёт документ.

## Границы модулей

- `extraction` содержит интерфейсы, JSON адаптер и mock реализацию.
- `validation` содержит проверки значений и готового файла.
- `templates` загружает описание полей, считает значения и заполняет DOCX.
- `storage` разрешает запись только в явно выбранный каталог и принимает только имя `.docx`.
- `orchestrator.py` управляет статусами и не знает о конкретном LLM провайдере.

## Почему LLM не пишет правовой текст

Генерация условий моделью делает результат трудно проверяемым. В этом проекте LLM может вернуть
только значения известных полей. Текст документа хранится в версионируемом шаблоне. Формулы,
валидация и проверка слотов выполняются обычным кодом. Такой результат проще тестировать и
сравнивать между запусками.

## Статусы

- `done` означает, что файл создан и прошёл проверки.
- `needs_input` означает, что не хватает обязательных данных.
- `failed` означает, что файл создан, но проверка нашла проблему.

Исключения чтения, извлечения, расчётов и рендера не преобразуются автоматически в `failed`.
При `needs_input` новый файл не создаётся, но существующий результат не удаляется.

## Интерфейсы и зависимости

`Extractor.extract(text, fields) -> dict` отделяет получение значений от конвейера.
`JsonLLMExtractor` принимает `TextCompletion.complete(prompt) -> str`; встроенного сетевого
клиента нет. По умолчанию допускаются две попытки разбора; ошибка внешнего клиента не обязана
повторяться. `MockExtractor` получает заранее заданные значения и игнорирует текст запроса.

`load_field_specs` читает YAML через PyYAML. `resolve_values` нормализует данные, вычисляет
деньги через Decimal и текст через num2words. `render_docx` использует docxtpl;
проверки читают файл через python-docx. `RequiredFieldsValidator` доступен отдельно,
но `run_pipeline` использует список missing из `resolve_values`, а не этот валидатор.

Публичный результат — `PipelineResult` со статусом, необязательным путём, кортежем недостающих
полей и кортежем `ValidationIssue(code, message)`. Точка входа экспортируется из пакета.

## Хранение и границы гарантий

`LocalOutputStore` принимает basename с расширением `.docx`, создаёт явно выбранный каталог
и возвращает путь. Конвейер всегда использует имя `synthetic-service-agreement.docx`;
версий и защиты от перезаписи нет. Это проверка имени, не полноценная песочница файловой системы.

Проверка обязательности основана на непустом значении, а не полной семантической проверке
элементов услуг. Проверка результата подтверждает ограниченный набор структурных признаков,
не юридическую корректность или визуальную пригодность документа.

Точное поведение и связь с тестами: [spec](specs/synthetic-document-pipeline.md).
Процедуры изменений: [разработка](runbooks/development.md) и [шаблон](template-authoring.md).
