# Архитектура

## Основной поток

`run_pipeline` связывает пять простых шагов.

1. `Extractor` получает текст и список полей.
2. `resolve_values` нормализует значения и проверяет обязательные поля.
3. Та же функция считает суммы строк, итог и сумму прописью.
4. `docxtpl` подставляет данные в готовый DOCX.
5. `RenderedDocumentValidator` ищет открытые слоты, маркер демо и таблицу услуг.

Если обязательных значений нет, конвейер возвращает статус `needs_input` и не создаёт документ.

## Границы модулей

- `extraction` содержит интерфейсы, JSON адаптер и mock реализацию.
- `validation` содержит проверки значений и готового файла.
- `templates` загружает описание полей, считает значения и заполняет DOCX.
- `storage` разрешает запись только в явно выбранный каталог и принимает только имя `.docx`.
- `orchestrator.py` управляет статусами и не знает о конкретном LLM провайдере.

## Почему LLM не пишет правовой текст

Генерация условий моделью делает результат трудно проверяемым. В этом проекте LLM может вернуть
только значения известных полей. Текст документа хранится в версионируемом шаблоне. Формулы,
валидация и проверка слотов выполняются обычным кодом. Такой результат проще тестировать и
сравнивать между запусками.

## Статусы

- `done` означает, что файл создан и прошёл проверки.
- `needs_input` означает, что не хватает обязательных данных.
- `failed` означает, что файл создан, но проверка нашла проблему.
