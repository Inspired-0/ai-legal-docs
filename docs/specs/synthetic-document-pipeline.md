# Синтетический DOCX: существующий контракт

Статус: описание реализации и тестов на 2026-10-18, не обещание production-валидации.

## Задача и границы

Заполнить готовый синтетический договор значениями из запроса, сохранив текст шаблона.
Scope и non-goals: [PROJECT.md](../PROJECT.md).

## Интерфейс и данные

`run_pipeline(request, extractor, fields_path, template_path, output_dir)` возвращает
`PipelineResult(status, output_path, missing, issues)`.
Входные поля описаны в [fields.yaml](../../templates/synthetic-service-agreement/fields.yaml).
Пользовательские поля — номер и дата, стороны/адреса/тестовые идентификаторы, список `services`.
Элементы списка: `name`, `quantity`, `unit`, `price`. Код добавляет номер строки и `amount`,
затем вычисляет `total_amount` и `total_in_words`.

## Поведение и инварианты

1. `MockExtractor` возвращает известные пользовательские поля из переданных значений;
   он не анализирует текст запроса. `JsonLLMExtractor` вызывает переданный `TextCompletion`.
2. JSON-адаптер отбрасывает неизвестные верхнеуровневые поля и ключи элементов списка,
   приводит скаляры к строкам, допускает JSON внутри code fence. По умолчанию делает две попытки
   при ошибке разбора/`ValueError`; после исчерпания выбрасывает `ValueError`.
3. `resolve_values` нормализует значения, вычисляет денежные суммы через `Decimal` и
   проверяет обязательные поля по непустому значению. Полной проверки типов/семантики нет.
4. Недостающие поля дают `needs_input`, `output_path=None` и список `missing` до рендера.
5. Результат записывается как `synthetic-service-agreement.docx` внутри `output_dir`.
   Повторный успешный рендер использует то же имя и может перезаписать предыдущий результат.
6. Проверки готового файла ищут незаполненные слоты, `SYNTHETIC DEMO` в основном тексте
   и первую таблицу с минимум тремя строками. Успех даёт `done`; найденные проблемы — `failed`
   с путём к уже созданному файлу и `issues`.
7. Ошибки чтения, извлечения, вычислений или рендера могут выходить исключениями.
   `failed` не является универсальной обработкой ошибок.

## Критерии и существующие проверки

| Критерий | Проверка |
| --- | --- |
| Фильтрация/нормализация JSON и ограничение повторов | `tests/test_extraction.py` |
| Обязательные поля; суммы строк 3000.00 и 4000.00, итог 7000.00 | `tests/test_fields_and_validation.py` |
| `needs_input` без пути результата; успешный рендер без слотов | `tests/test_pipeline.py` |
| Синтетические стороны, итог и 4 строки таблицы в результате | `tests/test_pipeline.py` |
| Размеры страницы, таблица и слоты соответствуют golden | `tests/test_template_structure.py` |
| Metadata исходного DOCX очищены | `tests/test_template_structure.py` |

## Непокрытые границы

Тесты не доказывают корректность произвольных цен/количеств, всех исключений, ветки `failed`,
всех способов обхода путей или внешнего клиента. Отсутствующее обязательное поле не удаляет
результат предыдущего запуска. Нельзя считать эти ограничения устранёнными без отдельной задачи.

## Совместимость

При изменениях сохранять публичные протоколы, статусы, схему примера и структуру шаблона,
если задача явно не меняет контракт. Новое поведение сначала описывать критериями и проверками.
